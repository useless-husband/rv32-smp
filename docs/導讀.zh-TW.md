# 初學者導讀

這份文件給專案作者自己看，目的是：看完之後能在面試或報告裡，用自己的話把這個專案
講清楚。假設你已經懂單核心的 rv32-pipeline，這裡只講「多核心一致性」多出來的東西。

## 一句話這專案在做什麼

把一顆單核心 CPU 變成「多核心」：好幾顆核心，每顆都有自己的小快取，它們必須對同一
塊記憶體看到一致的內容。難的不是「跑得動」，而是「證明它永遠正確」——所以用了三種
互相獨立的方法去驗，還故意放進五個經典 bug，證明這些方法真的抓得到。

## 它解決什麼問題

一顆核心讀寫記憶體很簡單。但如果有四顆核心，每顆都為了快而把資料「抄」一份到自己的
快取裡，問題就來了：核心 A 把某個變數改成 5，核心 B 的快取裡還是舊的 3——B 讀到 3
就錯了。**快取一致性協定**（這裡用的是 MESI）就是一套規則，保證「任何一次讀取，拿
到的都是最新寫進去的值」，就算值藏在別人的快取裡也一樣。這是每一顆多核處理器都必須
做對、而且極難驗證的東西。

## 7 個關鍵概念（每個配一個生活比喻）

1. **MESI 四個狀態**。每一行快取資料有四種身份：
   - **M（Modified，已改）**：我手上這份是最新的，而且只有我有，記憶體是舊的。
   - **E（Exclusive，獨佔）**：只有我有這份，而且跟記憶體一樣（還沒改）。
   - **S（Shared，共享）**：好幾個人都有這份，大家一樣、也跟記憶體一樣。
   - **I（Invalid，無效）**：我沒有這份，或我手上的不能用。

   *比喻*：一份公司文件。M＝只有你有、而且你改過的草稿；E＝只有你借出、還沒動；
   S＝影印給很多人看的公告；I＝你根本沒有或已作廢。規則是：**同一時間最多只有一個人
   能持有「可以改」的版本（M 或 E），一旦有人要改，其他人的影本都要作廢。**

2. **窺探匯流排（snooping bus）**。所有核心的快取掛在同一條「廣播線」上。有人要某一
   行資料時，就在線上喊一聲，其他人「窺探」到這個喊話，就知道該怎麼反應（把自己的副
   本作廢、或把最新的值交出來）。
   *比喻*：開放式辦公室裡大聲喊「誰手上有 X 檔案的最新版？」——聽到的人要嘛交出來、
   要嘛把自己手上的撕掉。這裡**一次只能有一個人喊**，所以大家對「誰先誰後」有共識。

3. **這條匯流排的順序就是「真相的順序」**。因為一次只做一筆交易，匯流排授權的先後
   就定義了每一行資料被改寫的先後。驗證時，我們就用這個順序當作「標準答案」。
   *比喻*：只有一支麥克風，誰拿到麥克風誰講話，大家聽到的順序一定一樣。

4. **原子操作與 LR/SC**。多核心常需要「不被打斷地讀—改—寫」，例如計數器加一、搶
   鎖。A 延伸指令提供 AMO（如 `amoadd`，一步到位加法）和 LR/SC（先「預約」一個位
   址，改好後若預約還在就寫入、否則失敗重來）。
   *比喻*：LR/SC 像「我先在這格貼便利貼預約，等我回來如果便利貼還在就寫，不在（有人
   動過）就重來」。**別人寫了這格，我的便利貼就要被撕掉**——否則我會蓋掉別人的修改。

5. **三個競態（race）才是真正的難點**。協定大部分是直覺的，難的是兩件事剛好同時發
   生：
   - **升級競態**：A、B 都有共享副本、都想改。兩個同時喊「我要升級成可改」，匯流排先
     讓 A 改，B 的副本就被作廢了——B 不能再「升級」一個它已經沒有的東西，要改成「重
     新讀一份再改」。
   - **寫回競態**：一行髒資料被擠出快取、暫放在「寫回緩衝區」還沒進記憶體。這時別人來
     要這一行，**必須由緩衝區回答**，因為記憶體裡還是舊的。
   - **保留競態**：我 LR 預約了，別人寫了同一行，我的預約一定要被清掉，SC 才會正確地
     失敗。

6. **三層驗證**。這是專案的靈魂：
   - **模型檢查**：把協定寫成一個小小的數學狀態機，用電腦**窮舉所有可能的狀態**（2–3
     個快取、1–2 個位址），檢查「永遠不會有兩個人同時能改」等性質。
   - **黃金記憶體檢查器**：在真的 RTL 跑的時候，旁邊有個裁判，記下每一次讀寫，確認每
     次讀到的都是「最新一筆寫入」的值。
   - **RTL 對模型比對**：硬體每做一個動作，就拿去問模型「你允許嗎？結果一樣嗎？」
   *比喻*：一份帳本，請三個互不相干的會計師用三種方法各查一遍，三個都說對才算對。

7. **偽共享（false sharing）**。兩個核心各改各的變數，本來不該互相干擾；但如果這兩個
   變數剛好擠在同一條快取行裡，硬體會以為它們在「搶同一份」，於是快取行在兩核間來回
   彈，變得超慢。把變數隔到不同快取行（padding）就快了近 3 倍。
   *比喻*：兩個人各寫各的筆記，卻共用一本簿子，每次一個人寫、另一個人就得把整本搶過
   去——明明互不相干卻互相拖累。

## 檔案導覽（哪個檔做什麼）

- `rtl/core.sv`：一顆核心（管線），從單核版加上 A 延伸指令、FENCE、`mhartid`。
- `rtl/l1d.sv`：**本專案最核心的檔案**——私有 L1 資料快取與 MESI 協定、寫回緩衝區、
  LR/SC 預約、窺探邏輯、以及上面講的三個競態的處理。五個 bug 也都是在這裡用 `BUG`
  參數切換的。
- `rtl/bus.sv`：窺探匯流排與仲裁器。
- `rtl/icache.sv`：指令快取（提取時也會窺探資料快取，所以 `fence.i` 跨核有效）。
- `rtl/sim/smp_top.sv`：把 N 顆核心＋匯流排＋記憶體接起來給模擬用。
- `model/mesi.hpp`：協定的抽象模型（檢查器與比對共用）。
- `model/mc.cpp`：模型檢查器（窮舉所有狀態）。
- `model/rv_iss.c`：黃金指令集模型，每核一份，lockstep 的「標準答案」。
- `sim/memcheck.h`：黃金記憶體順序檢查器。
- `sim/smp_main.cpp`：Verilator 測試框架，把上面三層驗證接在一起。
- `sw/runtime/smp.h`、`smp.c`：多核開機、fork/join、barrier、鎖。
- `tests/museum/`：五個重現 bug 的程式。
- `tests/programs/`：原子壓力、隨機壓力、偽共享、效能、litmus。
- `tools/`：效能、合成報告、變異測試、bug 博物館資料、HTML 報告。

## 10 個可能的面試問題與簡短回答

1. **什麼是快取一致性？為什麼需要？**
   多核心各有快取、會各抄一份資料；一致性協定保證任何讀取都拿到最新寫入的值，否則核
   心會讀到別人改之前的舊資料。

2. **MESI 四個狀態分別代表什麼？**
   Modified（只有我有、已改、記憶體是舊的）、Exclusive（只有我有、未改）、Shared（多
   人共享、都一樣）、Invalid（無效）。核心規則：最多一個可寫副本（M/E），要寫就先讓別
   人作廢。

3. **窺探匯流排怎麼運作？為什麼一次只做一筆交易？**
   每個快取掛在同一條線上，請求用廣播，其他快取窺探並反應。一次一筆讓所有核心對一致
   性事件的先後有一致看法——這個全域順序就是每一行的一致性順序，也讓驗證變簡單。

4. **講一個協定裡的競態，以及你怎麼解決。**
   升級競態：兩個快取都持共享副本、都想寫，各發 BusUpgr；匯流排先服務其中一個，另一
   個的副本被作廢。解法是：升級進行中若被窺探作廢，就把請求改成 BusRdX，重新把最新資
   料讀回來再寫。（可再講寫回競態、保留競態。）

5. **LR/SC 怎麼保證原子性？遠端寫入發生時會怎樣？**
   LR 在一個對齊顆粒上設「保留」，SC 只有在保留還在時才寫入並成功。別的核心寫了這個顆
   粒時，窺探會作廢這一行，同時清掉保留，於是後來的 SC 必定失敗、程式重試——這正是原
   子性的來源。

6. **你怎麼驗證協定是對的？**
   三個互相獨立的檢查器：窮舉式模型檢查（小規模下證明不變式）、黃金記憶體順序檢查器
   （每次執行確認每個讀值合法）、RTL 對抽象模型逐步比對。三者都過，bug 才躲得掉；變異
   測試顯示一行的錯誤都躲不過。

7. **這顆機器的記憶體模型是什麼？和 RVWMO 有什麼關係？**
   循序一致（SC）：核心循序執行、在單一點以程式順序完成每個存取，沒有 store buffer。
   SC 比 RISC-V 要求的 RVWMO 更強，所以 litmus 測試裡那些 RVWMO 允許的鬆弛結果一次都
   沒出現。FENCE 因此在硬體是空操作，但軟體仍下正確的 fence 以便移植。

8. **什麼是偽共享？怎麼修？**
   兩個無關的變數剛好在同一條快取行，硬體把它們當成同一份而讓快取行在核間來回彈，變
   很慢。把它們分到不同快取行（padding）就解決，示範裡快了約 3 倍。

9. **為什麼選窺探而不是目錄？代價是什麼？**
   窺探簡單、幾百行就寫完、而且能被模型檢查器窮舉驗證。代價是所有一致性流量被串列
   化，所以核數不能多。目錄較可擴展但狀態多很多、更難驗，列為未來工作。

10. **這個專案有什麼限制、哪裡可以繼續做？**
    只有模擬＋Yosys 估算、沒上板；4 核放不進目標 FPGA；只有一層私有 L1、沒有共享 L2
    或目錄；只有 RV32IMA。未來可做：目錄式協定、共享 L2、以及一個帶 store buffer 的弱
    記憶體模型實作（用 litmus 當驗收標準）。

## 建議的講解順序（報告用）

先講「問題」（多核各抄一份 → 會讀到舊值），再講「規則」（MESI＋窺探匯流排），接著
講「最難的三個競態」各一句，最後——也是最值得講的——「我怎麼證明它對：三層驗證＋把
五個 bug 放回去看它們被抓到」。最後用 `跑跑看.command` 或 HTML 報告現場展示一個 bug
被抓到的時間軸。
